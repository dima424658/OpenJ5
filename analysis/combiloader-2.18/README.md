# CombiLoader 2.18 и Январь 5.1

Разбор `combi_218_protivo.exe` из комплекта CTP-3.21. Здесь сохранены псевдокод REA/Ghidra для загрузчика, обмена по COM и обработчиков чтения, записи и очистки, а также дизассемблирование выбранных функций. Адреса относятся к виртуальным адресам PE при базе `0x400000`. Имена файлов отражают найденную роль функций. В псевдокоде сохранены сгенерированные имена, типы и адреса Ghidra. Для параметров, передаваемых в регистрах x86, приоритет у дизассемблирования.

- Исходный PE32 x86, 513 024 байта. SHA-256 `c1c0f2695ed217ddb4d9894ed34ad96ee7af8f428e28b0822809bb27b92c59aa`.
- Аналитический PE. SHA-256 `4fe9e9bd1ca0455f0ab5562281b6da3de4884456ff49e5b0eeb73ad4e7ce19d5`.
- REA 6.10.1, Ghidra 12.2. Идентификаторы Evidence записаны в заголовках результатов. Обзор исходного PE `ev_afa49ab397efb32d033754b105c4d0223426a555e72d136a173e7af2fe479c0c`. Импорты `ev_1fb0a7edbac212bbcf8cea9bbec23c50f229c534bb9577b4cede54ec91914c17`.

## Упаковка и шифрование

Внешняя точка входа `0x7987b0` распаковывает содержимое `MASKT` из `0x71d000` в область с началом в `0x401000`. Далее код заполняет таблицу импортов через `LoadLibraryA` и `GetProcAddress` и прыгает на `0x40141a`. Первичный проход REA по исходному PE нашёл 12 внешних импортов и одну локальную функцию с неполным телом. Для второго прохода я эмулировал цикл распаковки до `0x798896` и построил PE для статического анализа с восстановленными адресами и именами импортов. Код приложения и Win32 API при распаковке не исполнялись. [Листинг точки входа](disassembly/0x7987b0-packed-entry.asm.txt) · [Восстановленная точка входа](decompiled/0x40141a-application-entry.c.txt)

Исполняемый код анализируется после распаковки. Встроенный загрузчик ЭБУ дополнительно зашифрован CAST-256. Идентификация основана на четырёх S-блоках, функциях раунда и развёртке ключа из RFC 2612. Функция `0x404924` передаёт 144 полных блока по 16 байт в `0x401d4c` после инициализации `0x401a54`. Последние два байта берутся из массива напрямую. Изолированная эмуляция этих функций дала все 2306 байт полезной нагрузки побайтно как в захвате `combi-bootstrap-frames.bin`, SHA-256 `825864595df1bf7227fcb6ffa101544fdd095eed17f6f90576e09f0fde728258`. [Загрузка в XRAM](decompiled/0x404924-upload-bootstrap.c.txt) · [Развёртка ключа](decompiled/0x401a54-bootstrap-key-schedule.c.txt) · [Расшифровка блока](decompiled/0x401d4c-bootstrap-decrypt-block.c.txt) · [RFC 2612](https://www.rfc-editor.org/rfc/rfc2612)

## Код, исполняемый в ЭБУ

Полезная нагрузка захваченных кадров занимает `0xF400–0xFD01`. Это машинный код семейства 8051 для C509‑L. Дизассемблирование в s51 показывает инициализацию на `0xF400` и цикл приёма команд на `0xFC63`. Приёмник в ЭБУ (`0xFA64`) использует UART через `SBUF`, проверяет сумму и передаёт команду диспетчеру. Тот вызывает обработчики в диапазоне `0xF815–0xF9F5`. Таким образом, CombiLoader загружает в ОЗУ ЭБУ обработчики для дальнейшего обмена с ПК.

| Команда | Адрес | Что исполняет ЭБУ |
| --- | --- | --- |
| `11` | `0xF815` | Возвращает два байта, сохранённые стартовой пробой `0xF7CA`. |
| `12` | `0xF826` | Запускает стирание Flash и формирует статус `55` или `AA`. |
| `13` | `0xF842` | Собирает байт флагов из состояния, установленного при инициализации. |
| `14`, `15` | `0xF867`, `0xF88A` | Переключает банк и читает или программирует указанный участок Flash. |
| `16`, `17` | `0xF8BE`, `0xF8F3` | Читает или записывает EEPROM. |
| `19` | `0xF944` | Сравнивает банки. Если они различаются, проверяет, заполнен ли проверяемый банк целиком нулями или `FF`. |
| `1A` | `0xF99D` | Проверяет первый байт банка назначения. Если это `FF`, копирует данные из другого банка порциями по 128 байт. Иначе сразу возвращает `55`. |

Назначение обработчиков сверено с Windows-кодом и захватами. Условия внутри `19` и `1A` установлены по дизассемблированию. По ответам в захватах нельзя определить, выполнялась ли фактическая перезапись второго банка.

## Проверки обмена

- **Старт.** Первичный запрос отправляет `00`, читает байт эха и ожидает `55` следующим байтом. В `no-answer.dmslog8` передан только исходный `00`. Кадры передачи bootstrap используют XOR и подтверждение `55`. Подпрограмма отправки допускает до пяти попыток на кадр. Это другой механизм, чем ожидание включения блока в `janvar-flash`. [Первичный запрос](decompiled/0x4047e8-initial-probe.c.txt) · [Отправка кадра](decompiled/0x404804-send-bootstrap-frame.c.txt) · [Повторы](decompiled/0x40484c-retry-bootstrap-frame.c.txt)
- **Команды после загрузки.** Общий отправитель добавляет длину, байт команды `0x10 | cmd` и сумму по модулю 256. Он считывает эхо длиной с отправленный кадр во временный буфер. Сравнения содержимого эха в этой функции нет. Приёмник проверяет верхнюю границу длины `0x90`, сумму и старшую тетраду ответа `0x90`. Функция обмена дополнительно сверяет младшую тетраду с командой и делает до четырёх попыток. При отрицательном результате приёмника она вызывает восстановление обмена с паузой 500 мс и командой `18`. Захваты успешных операций не показывают эту ветку. [Отправитель](decompiled/0x404b9c-send-command.c.txt) · [Приёмник](decompiled/0x404c54-receive-response.c.txt) · [Повторы](disassembly/0x404d78-exchange-with-retry.asm.txt) · [Восстановление](decompiled/0x404d50-recover-transport.c.txt)
- **COM и тайм-ауты.** Настройки проходят через `GetCommState` и `SetCommState`. На ветке программирования в захватах использовались 38 400 бод, 8N2. В `SetCommTimeouts` подставляются отдельные значения постоянного тайм-аута чтения. Для стирания Flash код задаёт 8000 мс, для записи блока Flash 500 мс, для записи блока EEPROM 2500 мс. Значения относятся к параметрам COM, а длительность операции может включать повторные попытки. [DCB](decompiled/0x42f74c-configure-com.c.txt) · [Тайм-ауты](decompiled/0x42f954-configure-timeouts.c.txt) · [Стирание](disassembly/0x404e20-flash-erase.asm.txt) · [Запись Flash](disassembly/0x4050c0-flash-write-blocks.asm.txt) · [Запись EEPROM](disassembly/0x405384-eeprom-write-blocks.asm.txt)

В одном обработчике при типе `04` и выбранной записи Flash есть проверка четырёхбайтового маркера в образе на смещениях `0x6000` и `0xC000`. Для другой конфигурации добавляются `0x16000` и `0x1C000`. При совпадении показывается сообщение «Данный тип контроллера не поддерживает прошивки с защитой», операция прерывается до стирания. Это подтверждённая проверка конкретной ветки. Полная матрица проверок входных файлов и поведение защищённой прошивки в ЭБУ здесь не установлены. [Обработчик и вызовы сравнения](decompiled/0x40c030-write-handler-variant.c.txt)

## Сверка с захватами

- `write-flash` и `write2` показывают `13 → 11 → 12 → 512 × 15 → 1A`. На двух блоках различаются типы `04` и `00`, а также данные ответа `11`. Обе записи подтверждены. В `write2` полезная нагрузка совпадает со штатным `J5V05J16`.
- На втором блоке ответ `11` был `00 FF` при пустой Flash и `00 02` с `J5V05J16`. Код Windows трактует оба значения как содержимое ответа. Эти наблюдения не позволяют определить физическую микросхему по `11`.
- `read-flash` содержит `13 → 19 → 512 × 14`. В `clear-flash` после `13` видны только `11 → 12`. Сеансы EEPROM содержат четыре блока по 128 байт, а в `clear-eeprom` все 512 отправленных байт равны `FF`.
- Захваты подтверждают операции с Flash 64 КиБ и EEPROM 512 байт. Ветви Flash 128 КиБ и восстановления после сбоя изучены статически. Действия обработчиков, связанных с другими ЭБУ и форматом `.bir`, полностью не разобраны. [Эталонные захваты и результаты стенда](../../docs/diagnostics.md)

SHA-256 файла `write2.dmslog8` — `a7160078aeffcc112445b3f86607b13c99718f67ff2c47aca7ab8ec8761d4a2d`. SHA-256 `sencod-block2.bin` — `6857429d13b62fe0cd60f71cf59c4facfefa01df3555a72a3826855609e85b3e`.

## Воспроизведение

Запустить из корня worktree в Python-окружении с `pefile==2024.8.26` и `unicorn==2.1.4`. Параметр `--bootstrap-frames` включает побайтное сравнение с захватом.

```sh
python analysis/combiloader-2.18/make_analysis_image.py \
  /path/to/combi_218_protivo.exe /tmp/combi-analysis.exe \
  --bootstrap-frames /path/to/combi-bootstrap-frames.bin
```

Полученный PE служит входом для `open_binary` с провайдером Ghidra. Псевдокод получен через `batch_decompile`, листинги функций — через `procedure_assembly`. Исходный EXE, синтетический PE и захваты в эту папку не входят.
