# Сборка J5V05L19 из исходного кода

Штатный образ для Январь 5.1 `2112-1411020-41` и C509-L собирается в плоский файл `build/J5v05l19.bin`. Все 65 536 байт образа собираются из исходников Си и привязанных к ним правил SDCC. Для проверки и экспорта BIN используется Python 3. На macOS инструменты SDCC можно установить командой `brew install sdcc`. Проверено с SDCC 4.6.0 и GNU Make 3.81. [Руководство SDCC](https://sdcc.sourceforge.net/doc/sdccman.pdf)

Из корня репозитория:

```sh
make -C firmware
make -C firmware verify
```

Первая команда компилирует исходники через `sdcc`, линкует их через `sdld` и конвертирует Intel HEX в BIN. Конвертер проверяет контрольные суммы записей, уникальность адресов и покрытие всех 65 536 байт. В `firmware/build/` также сохраняются Intel HEX, листинги компилятора и карта линковки.

Вторая команда сверяет сборку с [эталонным BIN](../bins/J5v05l19.bin), проверяет положение векторов и процедур по карте линковки, сумму Flash и обе суммы областей калибровок. При расхождении она показывает первое несовпадающее смещение. Для отдельной копии эталона можно передать `REFERENCE=/путь/к/J5v05l19.bin`. Ожидаемый SHA‑256 приведён в [карте памяти](../docs/firmware.md#идентификация).

## Как устроена реконструкция

Назначение алгоритмов и калибровок сопоставлено с руководством CTP 3.21, картами J5 и обращениями из штатного кода. В карте символов указаны адреса, соответствия картам и места, где назначение ещё уточняется. [Руководство CTP 3.21](../docs/ctp321.pdf) · [Карта символов](symbols.md)

Правила `.peep` сохраняют соглашения о регистрах C509-L, форму ветвлений и точную раскладку инструкций. В одном месте две точки входа используют общие байты инструкций. Это перекрытие сохраняется правилом для процедур записи диагностических записей. [Карта символов](symbols.md)

## Что разобрано

- Переходы таблицы векторов собираются из `src/c/entry_vector.c`, пустые обработчики прерываний из `src/c/unused_vector.c`.
- Билинейная интерполяция таблиц в CODE и XDATA собирается из `src/c/bilinear_interp.c`, одномерная интерполяция из `src/c/a575.c` и `src/c/a611.c`.
- `src/c/` содержит перенесённые на C процедуры и калибровки. Линковщик размещает их по исходным адресам. `make verify` также проверяет адреса символов и размеры их секций.
- `src/c/rom_layout.c` хранит нулевое заполнение и 62 байта региона калибровок с ещё не подтверждённым назначением. Абсолютные адреса и размеры проверяются по карте линковки.

Для процедуры по `0xA429` SDCC дополнительно использует `src/c/accumulator.peep`. Эти правила выбирают короткие инструкции для операций над регистром аккумулятора. Условие, преобразование значения и порядок операций заданы в C.

В арифметических процедурах из `a33a.c`, `a381.c` и `a3f9.c` входы и выходы следуют соглашению штатной прошивки. Локальные правила `src/c/stock_registers.peep` преобразуют обращения к операндам C в инструкции для активного в момент вызова банка регистров. Эти файлы собираются с `--no-peep`, поскольку встроенные правила SDCC могут удалить запись в регистр результата, если штатный вызывающий код использует соглашение, неизвестное компилятору. [Руководство SDCC](https://sdcc.sourceforge.net/doc/sdccman.pdf)

Блок расчёта координат температурной оси `src/c/3396.c` встроен между двумя участками обработчика датчиков. Правила `src/c/coolant_axis.peep` используют частное и остаток одной инструкции деления. Переход к продолжению в C компилируется в сквозное выполнение. Проверка карты линковки закрепляет адрес продолжения `0x33C2` сразу после блока.

Следующие участки можно переносить из `.db` в именованные инструкции, сохраняя абсолютные адреса и проверяя каждое изменение командой `make verify`. Правила именования и ссылки на исходные наблюдения собраны в [списке символов](symbols.md). Текущий этап проверен сравнением образов на компьютере.
